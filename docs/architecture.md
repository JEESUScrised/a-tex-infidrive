# Архитектура YTDrive

Программа делится на библиотечные пакеты и две точки входа. Кодирование данных написано на Go. FFmpeg вызывается как внешний процесс и только собирает или разбирает видео.

```text
cmd/ytdrive  ─┐
cmd/server   ─┼─► internal/codec ─► internal/packets
              │                  └─► internal/video ─► internal/ffmpeg
              ├─► internal/jobs ─► internal/storage (SQLite + файлы)
              └─► internal/httpapi ─► web/
internal/youtube — интерфейс будущей официальной загрузки, без реализации
```

## Поток кодирования

1. Файл читается потоком. Параллельно считается SHA-256 исходных байт, по расширению берётся MIME, опционально поток сжимается gzip во временный файл.
2. Метаданные (имя, размеры, хеш, флаги) укладываются в один или несколько мета-пакетов.
3. Сжатые или исходные байты режутся на пакеты фиксированного размера. У пакета есть индекс, номер копии и CRC32.
4. Каждые N пакетов данных дополняются XOR-пакетом. Он восстанавливает один потерянный пакет группы.
5. Пакеты пакуются в кадры 1280×720. Один бит — блок 16×16 одного из двух уровней яркости. В кадре есть калибровка чёрного и белого, номер кадра и CRC заголовка.
6. Одинаковые кадры можно записать несколько раз. FFmpeg получает сырой RGB по stdin и пишет MP4 (H.264, yuv420p). Процесс запускается через `exec.CommandContext`, без shell.

Память кодировщика не зависит от размера файла: на диске лежит временная копия, в памяти — текущая XOR-группа и один кадр.

## Поток восстановления

1. FFmpeg отдаёт кадры RGB. Размер кадра может отличаться от 1280×720.
2. Декодер пробует логические сетки. Бит определяется средней яркостью внутренней части блока, порог берётся из калибровочных блоков того же кадра.
3. Кадр с битой сигнатурой или CRC заголовка пропускается. Повторный номер кадра не затирает уже принятые пакеты, но даёт второй шанс прочитать пакет, если первая копия была повреждена.
4. Пакет с неверным CRC32 отбрасывается. Принятые пакеты пишутся во временный файл по индексу, в памяти хранится только битовая карта.
5. Если в XOR-группе не хватает ровно одного пакета, он восстанавливается.
6. Если дыры остались, команда завершается ошибкой и выходной файл не создаётся.
7. Если метаданные просят gzip, поток распаковывается. SHA-256 сверяется с метаданными. Только после этого временный файл переименовывается в результат.

## Веб и задания

`cmd/server` поднимает `net/http`. Страница — обычные HTML, CSS и JavaScript из каталога `web/`.

Загрузка сохраняется в `data/objects/<id>/original`. На диске нет пользовательского пути, поэтому `../` в имени файла не выходит из каталога данных. Исходное имя хранится в SQLite и записывается в метаданные видео, чтобы восстановление вернуло имя и расширение.

`POST /api/files/{id}/encode` и `POST /api/recover` создают строку в таблице `jobs` и отправляют её в канал. Несколько воркеров разбирают канал. Размер канала и число воркеров ограничены, поэтому нельзя ни накопить бесконечную очередь, ни запустить произвольное число FFmpeg. Повторное кодирование того же файла, пока задание ещё активно, отклоняется.

Контекст сервера отменяет задания при остановке. `CommandContext` завершает дочерний процесс.

## YouTube

`VideoStorageProvider` описывает загрузку и проверку статуса. Реализация `Unconfigured` всегда возвращает ошибку. Кнопки «успешно загружено на YouTube» в интерфейсе нет: страница прямо пишет, что функция не настроена.

Дальше по этому интерфейсу можно добавить OAuth 2.0 и resumable upload YouTube Data API v3. Скачивание чужого ролика в обход API в проект не входит.

## Расширение формата

В заголовке кадра есть версия, режим пикселей и код избыточности. Сейчас используется режим «1 бит на блок» и коды «повтор», «XOR», «повтор+XOR». Значения для DCT, Reed-Solomon и fountain codes зарезервированы и декодером отвергаются как неподдерживаемые, а не молча игнорируются.
